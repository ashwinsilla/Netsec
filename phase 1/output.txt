Response:
In Arista AVD (`eos_designs`), the underlying template logic automatically uses the `Loopback0` IP address as the BGP router-id for your underlay/overlay routing. 

To configure the `Loopback0` IP address statically for a specific leaf switch (instead of dynamically deriving it from a `loopback_ipv4_pool`), you use the `loopback_ipv4_address` variable.

According to the schema, this variable expects the IP address **without the subnet mask** (AVD automatically applies `/32` for Loopback0).

Here is the YAML configuration for your leaf node:

```yaml
# Under your specific leaf node definition in the inventory or host_vars:
loopback_ipv4_address: 10.10.10.1
```

### Behind the Scenes
By simply defining the above variable, AVD will automatically generate the corresponding `eos_cli_config_gen` structured configuration for both the interface and the BGP router-id:

```yaml
# Auto-generated by AVD (for reference)
loopback_interfaces:
  Loopback0:
    description: EVPN_Overlay_Peering
    ip_address: 10.10.10.1/32

router_bgp:
  # AVD injects your loopback IPv4 address here automatically
  router_id: 10.10.10.1 
```

### Optional: Forcing it via Structured Config
If you ever need to manually override the BGP router-id to be different from `Loopback0` or want to force it explicitly through structured configuration on a node level, you can use the `structured_config` key:

```yaml
structured_config:
  router_bgp:
    router_id: 10.10.10.1
```

```yaml

# Defines the Loopback0 IP address used as the BGP Router-ID

l3leaf:
  nodes:
    - name: leaf1
      id: 1
      # Loopback0 IPv4 address (takes precedence over loopback_ipv4_pool)
      # This address will be used as the BGP Router-ID
      loopback_ipv4_address: 10.10.10.1
```

---

### Key Points

| Parameter | Value | Description |
|---|---|---|
| `loopback_ipv4_address` | `10.10.10.1` | Statically assigns Loopback0 IP, takes precedence over `loopback_ipv4_pool` |
| BGP Router-ID | `10.10.10.1` | AVD automatically uses Loopback0 as the BGP Router-ID |

---

### Alternative — Using a Pool (Dynamic Assignment)

If you prefer pool-based assignment instead of a static address:

```yaml
l3leaf:
  defaults:
    loopback_ipv4_pool: 10.10.10.0/24   # Pool from which Loopback0 IPs are derived

  nodes:
    - name: leaf1
      id: 1   # Leaf with id: 1 will receive 10.10.10.1/32 from the pool
```

---

### Notes

- AVD derives the **BGP Router-ID** from the **Loopback0** interface automatically — no explicit `router_id` key is needed under BGP settings.
- The `/32` mask is automatically applied by AVD to all loopback interfaces.
- `loopback_ipv4_address` should be specified **without** the prefix length (mask), as AVD always applies `/32`.
- When using `loopback_ipv4_pool`, the IP is calculated as: `pool_base_address + (node_id - 1)`.

Here is a minimal AVD YAML configuration to define VLAN 30 as an L2VLAN with VNI 1030 and a custom EVPN route-target:

```yaml
---
# L2VLAN definition for VLAN 30
l2vlans:
  - id: 30
    name: VLAN_30
    vni_override: 1030      # Statically assign VNI 1030 instead of deriving from mac_vrf_vni_base
    rt_override: "65000:1030" # Override the EVPN route-target to 65000:1030
```

### Key Points

| Field | Value | Purpose |
|---|---|---|
| `id` | `30` | VLAN ID |
| `name` | `VLAN_30` | VLAN name (descriptive label) |
| `vni_override` | `1030` | Statically sets the VXLAN VNI, bypassing the auto-derived value from `mac_vrf_vni_base` |
| `rt_override` | `"65000:1030"` | Overrides the auto-derived MAC-VRF route-target with a full RT string |

### Notes

- `rt_override` accepts **two formats**:
  - A **single integer** (e.g., `1030`) — replaces only the assigned-number field in the RT.
  - A **full RT string** (e.g., `"65000:1030"`) — overrides the entire RT including the AS number.
- `rd_override` is **not set** here; it will fall back to `rt_override` (`65000:1030`) by default per AVD schema precedence (`rd_override` → `rt_override` → `vni_override`).
- `vxlan: true` is the default and does not need to be explicitly set.
- This snippet is intended to be placed in a **tenant** or **global** variable file consumed by `eos_designs`.
